# Second-pass audit (Fable 5) — 2026-08-17

Scope: everything the first audit did **not** cover — the AI/messaging pipeline, crons, multi-tenancy, sessions, and the full unauthenticated surface. Two independent Fable 5 agents; every critical finding below re-verified by hand against the source and, where possible, against the live deployment.

The first pass fixed what was wrong with the *numbers* and the *boundaries between properties*. This pass is about what happens when someone — a guest, a stranger, a lapsed tenant — pushes on the edges. Nothing here is a regression from today's fixes; these are pre-existing and were simply outside the first scope.

---

## CRITICAL — a guest could receive the wrong message, or two

### 1. Dashboard "Approve" sends the browser's text, not the reviewed draft
`src/app/api/messages/reply/route.ts:86-146` — **verified by hand.**
The approve path sends `payload.body` straight from the client and only calls `resolvePendingDraft` *afterward*, with no read of the stored draft and no status check. Consequences:
- Approving on the dashboard after (or during) a WhatsApp "YES" sends the guest **two** messages — the exact double-send the code comment at `:34` claims is impossible.
- It sends whatever the browser POSTs, regardless of what was actually drafted and reviewed.
- A superseded/expired draft can still be "approved."

### 2. Approval is not atomic — double-send from three directions
`src/lib/pendingDrafts.ts:239-249`, `src/app/api/whatsapp/webhook/route.ts:359-447`.
`resolvePendingDraft` is read-modify-write with no compare-and-set, and the WhatsApp path does the slow OwnerRez send *between* the status check and the status write. Two concurrent approvals both pass the check before either writes. No dedup of inbound WhatsApp message IDs, so a Meta retry can replay the same "YES."

### 3. A stale swipe-reply approves an unrelated guest's message
`src/app/api/whatsapp/webhook/route.ts:79-103`.
When a WhatsApp swipe-reply's `contextWamid` doesn't resolve (wamid keys expire after 3 days), the code falls through to approving the **oldest pending draft overall**. So replying "yes" to an old approval card can send a message to a *different guest* than the one on screen.

## HIGH — the owner can be deceived about what he's approving; a sent message mis-recorded as failed

4. **Approval preview is truncated to 350 chars** (`src/lib/whatsapp.ts:299-300`) and, for non-English guests, Seni approves a model-generated English translation (`reply_english`) that is never cross-checked against the actual native-language text sent (`src/lib/aiReply.ts:36-43`). A prompt-injected guest message can make the English preview benign while the real outbound text differs.

5. **EDIT path sends unreviewed translation, and the guest-influenced `language` string is interpolated into the translator's system prompt** (`src/lib/translate.ts:88`, `src/lib/aiReply.ts:188`). Language names should be whitelisted.

6. **A successfully-sent message can be recorded as "failed"** (`whatsapp/webhook/route.ts:445-485`, `reply/route.ts:130-146`): the try-block spans past the OwnerRez send, so a failure in the *recording* step tells Seni "failed" for a message the guest already got. He resends → duplicate. No idempotency key on the OwnerRez POST.

7. **No session invalidation** (`src/lib/session.ts`, `src/proxy.ts` — verified: middleware never touches the DB). Deleting a team member, deactivating them, changing their password, or demoting their role does **nothing** to their existing cookie — role and org stay authoritative for up to 30 days. Only remedy today is rotating AUTH_SECRET (logs everyone out).

8. **Open signup + shared Anthropic key + trials that never expire** (`api/signup`, `src/lib/credentials.ts:252-257`, `src/lib/organizations.ts:97-102`). Public signup has no rate limit; every trial org can drive Anthropic spend on the platform key; expired trials are never demoted, so every org ever created stays in every cron loop forever.

9. **Cron fail-open cluster.** All six crons, `/api/webhook`, and the WhatsApp webhook run **open** if their (Vercel-Sensitive, un-introspectable) secret is ever unset. They log a warning but nothing alerts. This is the same shape as the webhook holes fixed earlier, just conditional on a secret going missing.

10. **check-messages, detect-reviews, weekly-trend-report are still Colombia-only** (`check-messages/route.ts:179` and siblings — no property group passed). Guest-message alerts, AI review drafts, and the weekly trend report ignore the other four properties entirely. Not a leak — a silent gap in coverage.

## MEDIUM

11. `check-messages` advances the "last seen" cursor **before** drafting/alerting (`route.ts:334`, verified) — a mid-run timeout permanently drops that guest message with no alert. Same failure class as past missed-message incidents; likelier now that multiple orgs share one 60s budget.
12. Billing lock is enforced only on pages, never on `/api/*` (`billingGate.ts` used only in `page.tsx`). A lapsed org's still-valid session reaches every data + AI route.
13. **Reflected XSS in `/api/oauth/callback`** (`route.ts:34-39`) — **confirmed live**: `?error=<script>...</script>` executes on the app's origin. `state` is generated but never verified.
14. No rate limiting on `/api/login` (**confirmed**) — unbounded online password guessing, slowed only by bcrypt cost 12. `/api/signup` returns 409 on existing email, enumerating accounts.
15. Public WhatsApp inquiries and chat-widget escalations have no global spend cap and don't validate the visitor phone before it becomes a WhatsApp `to` (`api/public/chat-widget/escalate`, `lib/chatEscalationFallback.ts`).
16. WhatsApp-source inquiries can be double-delivered by the fallback sweep (`lib/chatEscalations.ts:219-225` — no source filter).
17. Empty `draftReply` + "YES" sends an empty message (`whatsapp/webhook/route.ts:414`); webhook-created drafts use the assumptive chat-widget prompt with no language/service metadata (`webhookHandlers.ts:205-219`).
18. `daily-report` email gate checks Resend only (`executiveReport.ts:916`) — silently sends nothing once you move to Gmail-only.

## Confirmed solid (verified, not assumed)

All 26 `/api/admin/*` routes check `ADMIN_SECRET` and fail closed (enumerated). All debug routes are session-gated. Credential crypto is AES-256-GCM with a fresh IV per encrypt and a real auth tag; non-default orgs get no env-fallback credentials. Stripe webhook can't be driven by another account's events. The daily report's per-owner P&L isolation and per-property failure isolation hold. The legacy shared-password path is fully retired. Session tokens are tamper-resistant (HMAC, timing-safe). Redis-backed rate limiting on the public widget is cross-instance, not per-instance. Translation caching and the English no-op are correct. The `threadId` a message is sent to is never influenced by model output.

---

## Suggested order

The three CRITICALs are the only items where a wrong or duplicate message reaches a real guest — fix those first, and they're a focused change to two files (the approval path and the draft state machine). Then #6 and #7 (mis-recorded sends, session invalidation), then the fail-open hardening (#9) which is cheap insurance. The Colombia-only crons (#10) are the biggest *functional* gap — the other four properties are effectively running without the AI messaging layer — so that's a priority independent of security.
